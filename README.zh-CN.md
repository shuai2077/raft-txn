# txnkv — 基于 Multi-Raft 的 ACID 事务存储

一个分布式的、支持事务的键值存储，构建在
[`eliben/raft`](https://github.com/eliben/raft)（Go 语言教学版 Raft 实现）之上。

上游 Raft 保证的是 **单条命令** 的原子性。本仓库保证的是 **跨越多个 Raft 组的一组写入**
的原子性、隔离性与持久性 —— 这正是「做一个数据库」而不是「做一个复制日志」所需要的。

> English version: [README.md](README.md)

```
   N 个事务组（分片）                          1 个复制的授时服务
   ┌─────────┐ ┌─────────┐ ┌─────────┐        ┌─────────┐
   │ group 0 │ │ group 1 │ │ group 2 │        │   tso   │
   │ Raft ×3 │ │ Raft ×3 │ │ Raft ×3 │        │ Raft ×3 │
   │ + MVCC  │ │ + MVCC  │ │ + MVCC  │        │ + 时钟   │
   └────┬────┘ └────┬────┘ └────┬────┘        └────┬────┘
        └───────────┴───────────┘                  │
                    │                              │
               两阶段提交                          时间戳
                    │                              │
            ┌───────┴──────────────────────────────┴───────┐
            │                事务协调器                     │
            │      Begin / Get / Put / Delete / Commit     │
            └──────────────────────────────────────────────┘
```

## 能力

```go
tx, _ := store.Begin(ctx)
defer tx.Abort(ctx)

balance, found, err := tx.Get(ctx, "user:alice")   // 快照读
tx.Put(ctx, "user:alice", newBalance)               // 仅写入本地缓冲，尚未生效
tx.Put(ctx, "user:bob", otherBalance)               // 可能位于另一个组
commitTS, err := tx.Commit(ctx)                     // 对所有键原子提交
```

* **原子性（Atomic）** —— 跨越多个分片的提交要么全部生效，要么全不生效。不存在任何
  能让读者看到其中一半的中间状态。
* **隔离性（Isolated）** —— 每个事务在单一时间戳上读取快照；若另一个事务已经提交了它
  想要写入的键，则该写入被拒绝。（快照隔离；它究竟提供了什么、没有提供什么，见设计文档。）
* **持久性（Durable）** —— 每一次状态变更都是一条 Raft 日志条目，在向调用方返回之前
  已经落盘并被多数派复制。
* **容崩溃** —— 协调器在提交中途崩溃既不会丢数据，也不会永久阻塞它涉及的键；任何其他
  客户端都能把它的工作做完。
* **分片（Sharded）** —— 键被划分到多个相互独立的 Raft 组，每个组都是一个普通的 Raft
  集群。

## 快速开始

环境要求：Go 1.23+。

```bash
go build ./...
go test ./...                     # 全量测试，约 2 分钟
go test ./txn/                    # 事务协议，进程内运行，很快
go test ./cluster/                # 面向真实集群的端到端测试
```

`internal/raft` 是上游自带的测试套件，耗时最长。

> **关于不稳定的测试。** 该上游测试套件中的两个用例 ——
> `TestDisconnectAfterSubmit` 与 `TestBug_BecomeFollowerMissingPersist` —— 对时序敏感，
> 在负载较高时偶尔失败，极少数情况下 `TestCrashAfterSubmit` 也会。这是**继承自上游、而非
> 本次引入**的问题，而且是实测得出的结论而非假设：在修改 `internal/raft` **之前**那个提交
> 的 worktree 中运行同一包，15 轮失败 3 次（20%）；当前代码 10 轮失败 2 次（20%），且两次
> 失败的是同一批用例。两者在机器空闲时一起运行都能稳定通过。
>
> 压力测试另外暴露出三处不稳定成因 —— 测试集群之间的端口冲突、两个会活得比 `Shutdown` 更久
> 的 goroutine、以及在负载机器上过于紧张的测试等待预算 —— 均已修复，细节见提交历史。现在
> 反复运行整套测试，只会因上述继承自上游的用例而失败。

如果想观察机制本身而不是测试：

```bash
go run ./cmd/demo
```

## 一页读懂实现原理

**分片。** `Partitioner` 把键映射到组。每个组运行同一个 Raft 共识模块，作为持有键空间
某一片的复制状态机。

**多版本。** 一个键存放的不是单个值，而是一条版本链；每个版本都带有其写入者提交时的
时间戳。在快照 `T` 上读取，就是取版本链中 `CommitTS <= T` 的最新版本。删除同样是一个
版本，因此更早的快照仍然能看到旧值。

**两阶段提交。** 一个事务：

1. 从授时服务获取快照时间戳；
2. 在该快照上读取，并把写入缓存在内存中；
3. **准备（prepare）**：在它要写的每个键上安装 *意向锁*（intent lock），锁中携带待写入
   的值，位置在拥有该键的每个组里。此时什么都还不可见；
4. 从授时服务获取提交时间戳；
5. **封印（seal）** 某一个指定键 —— 即 *主键（primary）* —— 上的锁：这是**一条 Raft
   日志条目**，它永久性地决定了该事务的命运；
6. 在其余各组发布写入。

在第 3 步到第 5 步之间，事务仍然可以被回滚，因此在这个区间失败是安全的。从第 5 步起，
事务已经提交，任何操作都无法撤销它。

**提交点就是一条 Raft 日志条目。** 这是整个设计的核心。它意味着：任意组的任意成员 ——
而不仅仅是协调器 —— 都可以通过查询主键上的锁来判断事务发生了什么，并替它完成剩余的
工作。因此，协调器只是一种优化，而不是正确性的依赖。

**恢复。** 读者撞上一个锁时，会去主键所在的组询问事务的裁决结果，然后要么发布该写入
（已提交），要么丢弃该锁（已死亡）。它**绝不会**丢弃属于一个已提交事务的锁，因为那会
丢失一次已经确认过的写入。

**时间戳。** 授时服务本身也是一个 Raft 组，因此时间戳能够跨领导者更替而保持性质不变。
它以「窗口」为单位发放：一次 Raft 往返预留一大批时间戳，随后从内存中直接发放。新的
领导者无法消费前一任领导者的窗口 —— 它会在所有已占用时间戳之上重新预留一个窗口 ——
因此时间戳可能被浪费，但绝不会被重复。

## 现状与局限

这是一个学习性质的实现：它完整且有测试覆盖，但不是一个产品。在把它用于任何你在意的场景
之前，请先阅读[设计文档第 11 节](docs/02-transaction-design.md#11-not-implemented)。简要
来说：提供的是快照隔离而非可串行化；没有日志压缩与快照；不支持动态成员变更；没有版本垃圾
回收；组间 RPC 是串行执行的。

另有一条正确性限制值得单独说明，因为它属于**读一致性**而非「缺失的功能」：跨键快照读**不
保证**读到一个系统真实存在过的状态。每组独立的读屏障无法覆盖「事务已作出决定、但它对该组的
写入尚未被提议」这一情形（见 `docs/03-read-barrier.md` §1.5 与 §2.6）。**写入不会丢失**
—— 原子性已由提交协议保证 —— 但对同一个时间戳的多键读可能混合了两个瞬间。要消除它，需要在
授时服务侧引入完成登记表。
