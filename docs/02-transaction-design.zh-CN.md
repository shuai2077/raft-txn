# 设计：Multi-Raft 存储上的 ACID 事务

> English version: [02-transaction-design.md](02-transaction-design.md)

本文档说明有哪些东西被融合进了 `eliben/raft`，而更重要的是，*为什么*每个部件会被做成
现在的样子。它的写法是与代码对照阅读：每一节都会点出实现它的文件。

---

## 1. 问题

上游的 Raft 只为恰好一条命令提供原子性。一个 `Command` 由某一个组的状态机应用，落在该组
日志的某一个位置上，除此之外不会顺带发生任何事情。这对 `PUT` 来说足够了，对*单个键上的*
`CAS` 也足够了。

但对于以下情形则不够：

* **一个单位中的多个键。** 两个 `PUT` 必须同时落地，或者都不落地。两次彼此独立的 Raft
  提交可能被一次崩溃隔开，结果只有其中一个落地了。
* **位于不同组中的多个键。** 一旦键空间被分片 —— 这是让 Raft 日志具备扩展性的唯一途径
  —— 单个 Raft 组甚至无法表达这个操作。

因此，这里的工作就是构建一个位于 Raft 组联邦*之上*的东西，让横跨这些组的一组写入变得
原子、隔离且持久。这就是分布式事务协议，而业界收敛到的形态是 Google 的 Percolator
（TiKV 所采用，CockroachDB 也在其自有的变体中采用）。

## 2. 由此得到的架构

```
                    ┌──────────────────────────────────────────┐
   应用        ───► │  txn.Client  （协调器）                  │
                    │  Begin/Get/Put/Delete/Commit/Abort        │
                    └───────┬───────────────────────┬──────────┘
                            │                       │
              跨组两阶段提交                        时间戳
                            │                       │
        ┌───────────────────┴───────┐      ┌────────┴─────────┐
        │ txn.Participant 每组一个  │      │  txn.Oracle      │
        └───────────┬───────────────┘      └────────┬─────────┘
                    │ HTTP                          │ HTTP
   ┌────────────────┴───────────────┐      ┌────────┴──────────┐
   │ txnservice.Node                │      │ tso.Service       │
   │  ├─ HTTP 处理程序              │      │  ├─ HTTP 处理程序 │
   │  ├─ txn.RaftLog （适配器）     │      │  ├─ tso.Oracle    │
   │  └─ txn.Store （状态机）       │      │  └─ （状态机）    │
   │  └─ raft.Server ── RPC ──► peer│      │  └─ raft.Server   │
   └────────────────────────────────┘      └───────────────────┘
              组 0 .. 组 N-1                    授时组
```

自下而上阅读：

| 包 | 层次 | 职责 |
|---|---|---|
| `internal/raft` | 共识 | 未经修改的上游 Raft，加上 §9 中的钩子 |
| `txn` | 事务 | 整个协议：MVCC 状态机、协调器、锁解析 |
| `txnservice` | 传输 | 把单个 Raft 组通过 HTTP 暴露为一个 `txn.Participant` |
| `tso` | 时钟 | 一个由 Raft 复制的授时服务（`txn.Oracle`） |
| `cluster` | 装配 | 构建一个 Multi-Raft 集群，并故意把它弄坏 |

依赖规则是严格的：`txn` 对 HTTP、Raft 或各组的地址一无所知。它只看到 `Participant`
（一个接口）、`Oracle`（一个接口）和 `Partitioner`（一个纯函数）。其他所有包的存在
都是为了提供这些东西。

## 3. 隔离模型

**快照隔离，以 MVCC + 写写冲突检测实现。**

每个键都持有一条已提交版本的链，每个版本都盖上其写入者提交时刻的时间戳。在快照 `T` 上
读取的读者会遍历这条链，取 `CommitTS <= T` 的最新版本 —— 这就是整个读取路径。

```
key "a":   commit@10 "v1"     commit@25 "v2"     commit@40 delete
               ▲                  ▲                  ▲
          在 T=15 读取       在 T=30 读取       在 T=45 读取
           看到 "v1"          看到 "v2"          什么都看不到
```

删除是一个*版本*，而不是一次抹除，因此更早的快照仍然能看到那个值。这正是让一个长期运行
的事务的读取保持可重复的原因。

隔离性来自一条规则，它在状态机的 `prewrite` 处理函数中强制执行（`OpDelete` 和任何其他
写入一样，也是一种写入）：

> 如果 `k` 存在一个满足 `CommitTS > startTS` 的已提交版本，
> 则拒绝对 `k` 的写入。

因为它是在安装锁的同一条 Raft 条目内部求值的，所以检查与加锁之间不存在竞态。输掉的那个
事务会得到 `StatusWriteConflict`，并被整体回滚；重试循环会重新读取，并以新的快照重试。

为什么不做可串行化？因为快照隔离才是这一类系统实际上能廉价提供的保证，也因为真正有意思
的工程在于让*它*跨分片保持正确。§7.4 记录了要做到可串行化还需要什么。

## 4. 提交协议

两阶段提交，Percolator 风格，其中某一个键上的锁就是提交点。步骤如下，并标出实现每一步
的文件：

| # | 步骤 | 位置 |
|---|---|---|
| 1 | `startTS = oracle.ReadTS()` | `txn.Client.Begin` |
| 2 | 在 `startTS` 上读取，写入缓存在内存中 | `txn.Txn.Get/Put/Delete` |
| 3 | 准备：在每个拥有该键的组中安装意图锁 | `prewriteWrites`、`Store.prewrite` |
| 4 | `commitTS = oracle.CommitTS(startTS)`，在准备之后 | `txn.Txn.Commit` |
| 5 | **主键**：把 `commitTS` 写入主键上的锁，然后发布它的写入 | `commitPrimary`、`Store.seal` + `Store.commit` |
| 6 | 次级组：发布它们的写入 | `commitSecondary` |

有三项选择承载着正确性论证。

### 4.1 主键，以及为什么时间戳要在 prewrite *之后* 获取

主键被确定性地选为写集合中最小的键（`primaryKeyOf`），因此任何协调器或解析器无需彼此
协调就能得出同一个答案。

在所有锁都已就位*之后*才获取 `commitTS`，正是「推高」规则得以成立的原因：任何其他在
`startTS` 上观察到我们这把锁的事务，其提交时间戳必然大于我们即将拿到的 `commitTS`。
如果先把时间戳取回来，这个保证就消失了。

### 4.2 `seal` —— 原子提交点

安装一把锁并不决定任何事情：锁里携带的是*待定*的值，而读取仍然看到上一个版本。事务是在
某一次特定的写入上才成为已提交的：

```
CmdSeal{Key: primaryKey, TxnID, StartTS, CommitTS}
```

封印主键上的锁会记录下这个决定，并把该组的事务状态改为已提交，而这一切是**一条 Raft
日志条目**。每个副本要么有它、要么没有 —— 不存在可被观察到的中间状态。从那条条目起：

* 事务已经提交，而且是持久地提交，即使协调器再也不会运行；
* 任何其他成员、以及任何其他*组*，只要发现该事务的某把次级锁，就能查明这个决定并完成
  剩余的工作。

最后一点正是 `Txn.Commit` 中提交时故障路径返回 `CommitUnknownError` 却仍然报告成功的
原因：事务确实已经提交了，唯一失败的事情是协调器得知这个答案。在那一刻回滚才是 bug。

### 4.3 崩溃的协调器为何是安全的

协调器不属于正确性论证的一部分 —— 它只是一个恰好消息灵通的客户端。任何它没能完成的事
情，都会由下一个碰到这些锁之一的读者，依照 §5 的解析流程完成。

## 5. 锁解析：安全攸关的部分

一个发现外来意图锁的读者必须判断这把锁所属的事务是否已经提交。判断错了，往一个方向会
丢失一次已被确认的写入；往另一个方向，则会让一个已经被另一个读者观察到的值复活。

规则如下，实现在 `txn.Client.resolveLock` 和 `txn.DefaultResolver` 中：

| 对锁的观察结果 | 动作 |
|---|---|
| 锁记录本身携带一个 `CommitTS` | 属主已提交：**发布**这次写入 |
| 主键的事务状态是 `committed` | 已提交：**发布** |
| 主键的事务状态是 `aborted` | 已死亡：**丢弃** |
| 主键仍处于 `prepared`，租约有效 | 属主有权完成：**等待**，然后重新探测 |
| 主键仍处于 `prepared`，租约已过期 | 属主未在刷新它：**请求主组记录一次中止** |
| 主键所在的组没有该事务的任何记录 | 既无决定、也无须尊重的锁：**请求它记录一次中止** |

最后两行是 compare-and-abort（比较并中止），而不是推断，这一区别至关重要。在这次改动之前，
规则是「租约已过期，所以协调器已经消失：丢弃」，而它会丢失已提交的写入：租约只说明属主已经
停止刷新这把锁，并不说明它已无法封印提交点。主组在被请求时会重新检查自己的状态，因此如果
属主赢下了这场竞争，它会回答 `committed`；否则它会记录 `aborted`。详见
`docs/03-read-barrier.md` §2。

以下安全性质是这一切所保障的：

> 读者在丢弃任何一把锁之前，必须先**通过主组**确认该事务已不可能提交。主组是这件事的唯一
> 权威，而且这个答案必须是通过 Raft 记录的*决定*，而不是从时钟**推断**出来的结论。

注意解析器*不*做什么：它不依据自己撞上的那把锁的年龄来作决定。那把锁的年龄不能说明它
所属的事务是否已提交，因为决定存在于另一个组里。

### 5.1 为什么状态机跟踪事务状态，而不只是 `CommitTS`

次级锁永远不会被封印 —— 只有主键锁会。因此，发现一把次级锁的读者无法从这把锁里读出决定。
它必须去问主键所在的组，而它要问的是该事务的*状态*：

```
LockInfo{ Key, TxnID, Primary, StartTS, CommitTS, ActorCommitTS, State, ExpiresAt }
```

`State` 就是让解析变得可判定的那个字段。`ActorCommitTS` 是解析器得以知道该用哪个时间戳
去完成一次次级写入的途径（`finishLock` 把它传下去，`Store.commit` 用它来发布）。

## 6. 授时服务（`tso`）

事务需要一个全局性质，而本地计数器给不了这个性质：在整个集群范围内、跨越领导者更替，
时间戳绝不重复，也绝不倒退。

因此，授时服务和其他一切一样是一个复制状态机，并采用窗口化的分配方式：

```
   0            8                       16
   |------------|------------------------|
   已被占用     领导者 2 的窗口          领导者 3 的窗口
```

* `allocated` —— 一个全局高水位：凡是小于或等于它的时间戳都已被占用。它只能通过一条
  复制的 `CmdAllocate` 增长。
* 每一次分配都会指明它为哪个**成员**预留。一个节点只从属于自己的预留中发放时间戳，
  并且从内存中支出，因此发放一个时间戳不需要任何 Raft 往返。

按成员预留的理由正是故障转移的论证。新的领导者重放日志，发现 `allocated = 16`，并且
（另外）发现前一任领导者持有窗口 `(8, 16]`。它无法知道那个窗口已经被发放了多少，因此
它不能发放其中任何一个。它为自己预留 `(16, 24]`，并从 17 开始。时间戳 9..16 被**浪费**
掉 —— 这是刻意付出的代价 —— 而且没有任何一个会被重复。
`TestNewLeaderCannotSpendPredecessorsWindow` 直接锁定了这一点。

## 7. 设计决策与被否决的方案

### 7.1 协调器如何从 Raft 中取回答案

上游的模型是异步的：`Submit` 返回一个索引，答案稍后到达一个共享的 `commitChan`，由应用
把两者关联起来（Part 4 的提交订阅）。事务协调器无法使用这种方式，因为一个事务不是一条
命令 —— 它是一次*对话*，每一步的输入都取决于上一步的输出。为每一步重建索引关联，只会
重复造一套机械装置而没有任何收益。

因此加入了 `Server.Apply`：提议、等待该条目提交、返回状态机的答案。其中的影响在代码中
已经逐一写明：

* 状态机**只**从提交路径被应用，因此每个副本的状态都是其日志的函数；
* 状态机在共识锁**之外**运行，因此应用可以自行加锁，而不会拖住选举或在关闭时死锁；
* `Apply` 带超时，因为一个没有多数派的领导者永远无法提交，而让调用方挂住比告诉它结果
  未知更糟。

### 7.2 加锁，而不是乐观并发

另一条路 —— 在提交时校验读集合 —— 在这里无法跨组工作，因为它需要用每个组的版本历史去
原子地与所有其他组的版本历史对照检查。锁把决定放在数据所在之处：一个组、一条 Raft 条目、
一次原子状态转换。

### 7.3 租约作为活性机制

系统中没有分布式死锁检测器，也没有协调器心跳。锁只是携带 `ExpiresAt`。读者撞上一把已过期的
锁时，会请求主组记录一次中止；只有在该决定存在之后，它才可以丢弃这把锁；在那之前它会等待。
因此，协调器崩溃所付出的代价是*延迟*，其上限是租约时长，而绝不是永久不可用。

租约**刻意不**单独授权回滚。把「租约已过期」当成「属主已死」是一种**推断**，而它并不成立：
属主可能只是慢，而不是已经死亡；丢弃它的次级写入会丢失一笔已提交的事务
（见 `docs/03-read-barrier.md` §2）。租约界定的是读者等待多久；而通过 Raft 排序的*决定*才是
使回滚安全的东西。两套机制，各司其职。

租约之外的另一条路（基于成员关系的活性服务）会引入第二个需要推理的共识系统。

### 7.4 可见性是严格的，而且读规则与冲突规则必须互补

可见性是 `CommitTS < snapshot`；冲突检测是 `CommitTS >= snapshot`。两者**必须**严格互补。
这不是风格选择。

最初的实现用的是 `<=` 和 `>`。这两条规则在一条宽度为单个时间戳的区间上互相矛盾：一个恰好在
快照时间戳上提交的版本对读取可见，却**不**阻塞写入。于是事务可以先读到一个值，被一个恰好
在同一时间戳提交的并发写入者抢先，然后覆盖掉一个它已经观察到的提交 —— 这就是经典的丢失
更新，而两个事务都报告成功。

`TestStoreNoLostUpdateAtTheSnapshotBoundary` 直接锁定了这一点。

严格的可见性有两个值得说明的后果，因为不说清楚它们会令人困惑：

* **事务需要读回自己的写入才能看到它吗？** 不需要。它自己的写入缓存在本地，`Txn.Get`
  会先查这个缓冲。
* **在边界上看不到某个值是正确的。** 在时间戳 `C` 上的提交在快照 `C` 上不可见，在 `C+1`
  上可见。因此形如「提交后立即可见」的断言必须改为在 `C+1` 上读取。

### 7.5 跨键快照读与读屏障

只读事务读取每一个键都要经过它自己的一次 Raft 往返，且全部在同一个读时间戳上。读时间戳
本身并不保证所有在它之下提交的事务都已在每个组中变得*可见*：

```
T1 在快照 S 上读取 A 和 B
T2 在 c2 < S 处提交，它对 A 所在组的写入已被应用
                         而它对 B 所在组的写入尚未被应用
=> T1 看到 A 的新值和 B 的旧值：一个不一致的快照
```

**读屏障已经实现**（docs/03-read-barrier.md）。每个事务在首次从某个组读取之前，会先对
该组取一条空操作日志条目；由于 Raft 按日志顺序应用条目，等待那条条目被应用就证明了该组
已经应用完它日志中排在它之前的所有内容。论证见设计文档，同时也给出了它*不*提供的性质：
每组独立的屏障无法覆盖一个已经作出决定、但其写入尚未被提议到该组的事务。要补上这一点，
需要一道针对授时服务的屏障 —— 一张记录哪些已分配时间戳已经完成的登记表 —— 而这件事尚未
实现。

### 7.6 租约-回滚竞态（已修复）

追查剩余的守恒性失败时，暴露出比读偏斜更严重的问题。在一次静止运行之后，一个账户的版本
链中包含提交时间戳 44，而另一个账户的版本链中没有：一个事务在一个组提交了，在另一个组却
没有提交，而这恰恰是本设计存在就是为了防止的原子性违背。

其机制与修复方案见 docs/03-read-barrier.md §2。简言之，恢复过去是从租约失效去**推断**死亡：
读者发现一把已经过期的锁，其主键尚未被封印，便断定属主已死并把这把锁回滚；此后协调器封印
了主键，从而提交了一个其另一笔写入早已被丢弃的事务。

恢复现在是一种**通过 Raft 记录的 compare-and-abort**。租约仍然决定*何时*可以尝试恢复，
但中止是一条携带 `RecordDecision` 的 `CmdRollback`，在主键所在的组应用，它会先重新检查
事务的状态：如果属主赢得了竞态，它返回 `StatusAlreadyCommitted`，否则持久地记录
`StateAborted`。`Store.seal` 拒绝封印一个已中止的事务，`Txn.abortLockedGroups` 在任何次级
组之前先中止主键。因此，发布需要提交决定，丢弃需要中止决定，而两者都是在同一个组上按同一
顺序应用的单条条目 —— 不存在能让一笔写入被发布、另一笔却消失的交错。

`Txn.verifyLocksHeld` 仍然保留，作为一项廉价的提交前检查，把丢失的锁转化为一个干净的、
可重试的 `LockRolledBackError`，而不是一次白费的提交。

### 7.7 有意不提供可串行化

快照隔离允许写偏斜：两个读取重叠集合、写入不相交键的事务可以双双提交，产生一个没有任何
串行顺序能够解释的状态。要防止它，要么需要读锁（这会重新引入死锁，因而需要死锁检测），
要么需要一个可串行化的校验阶段。这是一项实实在在的工作，而且它是可分离的（它会给
`prewrite` 增加一次读集合检查），而把 SI 标称为可串行化来假装已经拥有它，比没有它更糟。

### 7.8 单组快速路径

当一个事务的每一个键都位于同一个组时，`CmdPrewrite` 可以在创建这些锁的*同一条*日志条目
中提交这些写入（`OneShot`）。这之所以成立，恰恰是因为整个写集合处于同一个原子单元中，
而且它把 Raft 往返次数减半。它是可选启用的，且默认关闭，因为真正有意思的是通用协议，
而快速路径不应成为测试默认演练的对象。

## 8. 正确性论证概述

**原子性。** 主键封印是一条 Raft 条目，因此它要么被所有副本观察到，要么无人观察到。在它
之前，不存在任何版本；在它之后，每一把锁都可以被任何成员朝提交方向解析。读者永远看不到
一个部分完成的事务，因为部分状态只以*锁*的形式存在，而读取永远不会穿透锁。

**隔离性。** 读取取快照上或快照之前的最新版本。如果存在更新的版本，写入就被拒绝。两者都
在键所属组上的同一条 Raft 条目内作出决定，因此相对于对该键的任何其他写入，检查与动作是
原子的。

**持久性。** 每一次状态转换 —— 安装锁、封印、发布一个版本 —— 都是一条 Raft 条目，因此在
客户端得到应答之前已经落盘并被多数派复制。恢复就是日志重放，而状态机是确定性的，因此重放
会精确地重现该状态。

**活性。** 崩溃的协调器留下的锁会随其租约失效，而下一个撞上它的读者会回收它 —— 但方式是
**询问**，而不是假定。租约只说明属主已经停止刷新；它并不说明属主是否仍能封印。因此读者会
请求主组记录一次中止，而主组会在该事务已经提交时拒绝这一请求。于是恢复成为一条通过 Raft
记录的*决定*，而不是从时钟**推断**出来的结论（该推断为何会丢写入，见
`docs/03-read-barrier.md` §2）。没有多数派的组无法取得进展，但它也无法破坏任何东西：提议
会失败，调用方会重试。

**唯一没有被保护的一点：** 协调器可能在主键封印*之后*、完成次级写入*之前*死亡，留下一些
其事务已经提交的锁。读者会解析它们，因此这些写入最终会变得可见 —— 正确，但有延迟。这是
本设计可见的代价，§4.3 解释了为什么这是*正确的*取舍。

## 9. Raft 核心中改动了什么

`internal/raft` 是上游 `part3/raft` 加上以下内容。每一处都在源码中标记为本地扩展；
完整理由见 `docs/01-raft-analysis.md` §5。

| 改动 | 目的 |
|---|---|
| `StateMachineHandler` / `Server.SetHandler` | 让一个组*成为*状态机 |
| `Server.Apply` | 同步的提议并应答 |
| 状态机从提交路径、在锁之外应用 | 顺序保证 + 一个真正能终止的关闭流程 |
| `leaderId` 跟踪、`Server.LeaderID` | 一跳领导者发现 |
| 连接被跟踪并在关闭时关闭；接受循环由 `Stop` 唤醒 | 真正会终止的关闭 |
| 在投递提交时检查 `stopChan` | 不读提交的客户端无法卡住关闭 |

其余一切 —— 算法、加锁纪律、持久化模型、RPC 接口，以及整套上游测试 —— 都未被改动。这种
克制是刻意的：重点在于展示一个事务层需要共识提供什么，而不是重写共识。

## 10. 测试策略

两个独立的层次，因为这两类 bug 是不同的：

**协议测试（`txn/`）** 在进程内运行状态机和协调器，配以一个可脚本化的授时服务和一个可
注入的时钟。它们覆盖那些在真实集群中很难刻意制造的情况：某一条特定的版本链、某一个特定
的 `LockedError`、一次 exactly-once 重试、一个乱序到达的提交时间戳。`directLog` 测试夹具把
命令直接应用到存储上，而这正是 Raft 领导者所做的事减去复制。

**系统测试（`cluster/`）** 通过 HTTP 搭建一个真实的 Multi-Raft 集群并把它弄坏：对一个组
做分区、隔离少数派、让领导者崩溃、从存储重启整个集群、让授时服务故障转移，以及在提交
中途放弃一个协调器。它们断言用户会在意的性质 —— 跨组原子性、可重复读、并发转账下某项
不变量的守恒 —— 外加最重要的那条内部性质：**副本之间一致**。

有两条测试设计上的教训被记录在代码里，因为弄错它们付出了真实的调试时间：

1. **在一个快照上审计不变量。** 用各自的事务读取每个账户会采样两个瞬间；期间有一笔转账
   提交，就会让总和看起来是错的，而每个事务其实都是正确的。存储没有问题；断言有问题。
2. **对租约建模，而不是操纵时钟。** 早期版本的恢复测试会移动一个假时钟，让锁立刻过期。
   它很脆弱 —— 取决于锁恰好是在什么时候被打上时间戳的 —— 并且以一种掩盖了真正的问题的方式
   不稳定。现在的测试使用一个很短的、真实的租约并重试，而这正是真实应用会做的事。

上游 Raft 测试套件按原样运行。`TestDisconnectAfterSubmit` 和
`TestBug_BecomeFollowerMissingPersist` 对时序敏感，在这台机器上相对于*未修改的*上游以
相近的比例偶发失败；这是继承来的性质，不是回归，而且它是被测量出来的，不是被假设的。

## 11. 未实现

这里明确列出，因为一份省略自身局限的设计文档是没有用的：

| 缺口 | 需要做什么 |
|---|---|
| **可串行化** | 在 `prewrite` 中加入读集合校验阶段，或者读锁加死锁检测 |
| **日志压缩 / 快照** | 上游核心没有这个能力，而一个长期存活的事务存储比 KV 存储更需要它 |
| **动态成员变更** | 上游没有这个能力；重新分片需要它 |
| **每组状态机的复制** | `txn.Store` 在重启时从该组的日志重放。基于快照的做法需要序列化版本链和锁表 |
| **旧版本的垃圾回收** | 版本链会无限增长；真实系统会丢弃低于最老活跃快照的版本 |
| **批量/并行的组间 RPC** | prewrite 和 commit 目前是逐个组串行地走过的 |
| **读租约 / read index** | 今天每一次读取都是一次 Raft 往返；上游 §8 的优化在这里适用 |
| **跨组死锁避免** | 之所以*不*需要它，只是因为 prewrite 是无等待的。加入读锁就会让它变得必要 |
