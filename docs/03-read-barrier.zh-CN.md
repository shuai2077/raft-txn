# 03 — 读屏障，以及租约回滚竞态

> English version: [03-read-barrier.md](03-read-barrier.md)

本文涵盖两件事，而它们最终被证明是同一次排查：

1. **读屏障** —— 已实现，并附有其正确性论证，以及它*不*提供的性质。
2. **一个租约回滚竞态** —— 由那次排查发现，已部分修复，且仍然未解决。这里连同证据一并描述，
   因为它正是 `TestConcurrentTransfersPreserveInvariant` 至今仍间歇性失败的原因。

---

## Part 1 — 只读快照缺失了什么

### 1.1 缺口

一个只读事务从授时服务取一个时间戳 `S`，然后对每个键各自做一次 Raft 往返来读取。共识为每个
*组*给出了线性一致的历史，但没有任何东西让这两次读对齐到同一个全局瞬间：

```
T1 reads A and B at snapshot S
T2 committed at c2 < S, and its write to A's group is applied
                          while its write to B's group is not
=> T1 sees A's new value and B's old value: an inconsistent snapshot
```

两次读各自都是正确的，而且都处在同一个时间戳上。但这个快照仍然不是系统曾经处于过的某个状态。

### 1.2 机制

`CmdBarrier` 是一条空操作命令。把它追加到某个组的日志，并等待它被*应用*，就证明了排在它之前的
每一条日志条目都已被应用，因为 Raft 按日志顺序应用条目。因此，事务第一次从某个组读取之前，会先
对该组取一次屏障。

顺序论证如下：

| 事实 | 原因 |
| --- | --- |
| 若 `T2` 的提交时间戳为 `c2 < S`，则 `S` 是在 `c2` 之后分配的 | 授时服务发放的时间戳严格递增 |
| `T2` 是在封印其主键之后才分配 `c2` 的 | 提交时间戳在预写（prewrite）之后、且在锁存在之后取得 |
| `T2` 对组 `G` 的写入是在那次封印之后被提议的 | 写入发生在决定之后 |
| 该读在 `G` 上的屏障是在 `S` 之后、因而也是在封印之后被提议的 | 屏障在 `S` 之后 |
| 因此 `T2` 对 `G` 的写入在 `G` 的日志中先于该屏障 | 追加顺序 |
| 因此当屏障返回时，`G` 的领导者已经应用了它 | Raft 按日志顺序应用 |

边界很重要：可见性是严格的（`CommitTS < snapshot`，见 docs/02-transaction-design.md §7.4），
因此 `G` 需要提交时间戳*低于* `S` 的每一个版本。恰好等于 `S` 的版本不可见，并且正确地不存在。

### 1.3 已实现的部分

| 部件 | 位置 |
| --- | --- |
| `CmdBarrier`，一条空操作命令 | `txn/command.go` |
| 屏障的应用 | `txn/store.go`（`Apply`） |
| `AppliedCommitTS`，即已应用水位 | `txn/store.go` |
| `Participant.Barrier` | `txn/types.go`、`txn/raftadapter.go`、`txnservice/client.go` |
| `POST /txn/barrier/` | `txnservice/service.go` |
| 首次读取时惰性触发、每组一次的屏障 | `txn/client.go`（`ensureReadable`） |
| Raft 核心上的 `CommitIndex`，用于诊断 | `internal/raft/raft.go`、`server.go` |

两处值得保留的实现细节：

* **屏障以空 body 的 POST 发送。** 当 body 为 nil 时，传输层会选择 GET，而该路由是 POST。这耗费
  了真实的调试时间：故障表现为 `HTTP 405`，随后又表现为一个领导者路由错误，而不是任何提到该
  方法的报错。
* **路由失败在 `Txn` 层重试，而不是在客户端层。** HTTP 客户端自己追踪领导者提示；进程内适配器
  则把错误交还给它的调用方。在 `ensureReadable` 中重试可以同时覆盖这两者。重新提议一次屏障总是
  安全的 —— 它不改变任何状态，而更靠后的位置只会使它成为*更强*的屏障。

### 1.4 水位是可观测性工具，而不是机制本身

`AppliedCommitTS` 记录状态机所见过的、已应用的最高提交时间戳，它在一次封印和一次版本发布时都会
更新。它是测试或运维人员用来检查该保证、而不是凭空相信它的手段：「这个组已经应用了直到 `X` 为止
的全部内容」。它被刻意设计成**不是**屏障所等待的对象，因此一个损坏或陈旧的水位无法削弱屏障。

### 1.5 每组屏障并不提供什么

**这就是那处重要的局限。** §1.2 中的论证只覆盖了在屏障被提议时、已经被提议给 `G` 的那些写入。
考虑一个事务 `T2`，它：

1. 取得提交时间戳 `c2 < S`，
2. 在组 `A` 中封印其主键（因此它已被决定），
3. 还*尚未*把它的写入提议给组 `B`。

一个对 `B` 取屏障、随后在 `S` 上读取 `B` 的读者，会漏掉 `T2` 对 `B` 的写入，即便 `c2 < S`。该屏障
在日志中位于那次写入到达*之前*，因此应用顺序对此证明不了任何东西。从事务的提交时间戳到它全部
写入发布完成之间的这段窗口，是一个每组屏障无法弥合的真实漏洞，因为屏障没有任何可以排序的对象。

实测：在屏障实现之后，`TestConcurrentTransfersPreserveInvariant` 仍会失败约 **25 次中 4 次**，
而在审计之前加入 300 ms 的静止窗口并没有改变这一点（30 次中 4 次）。因此对于跨键守恒检查来说，
屏障是必要的，但并不充分。

### 1.6 要真正补上这个缺口需要什么

所缺失的信号是全局性的：「每一个提交时间戳低于 `X` 的事务都已经发布了它的全部写入。」每组屏障
无法表达它。标准形态是**针对授时服务的读屏障**：

* 授时服务按每个已分配的时间戳跟踪拥有它的事务是否已经结束；并且
* 想要快照 `S` 的读者会等到 `S` 以下的全部工作都已结束，或者在一个*安全点*上读取 —— 该安全点
  只有在上述条件满足之后，授时服务才会推进。

这是一项真正的设计改动 —— 授时服务需要获知完成情况，这意味着要么由各组向它汇报进度，要么由
协调器汇报完成，此外还需要一条规则来处理中途死亡、必须被核销的事务。它不是一处局部修复，这里
也没有实现它。

## Part 2 — 租约回滚竞态

### 2.1 排查发现了什么

追查剩余失败时，发现了比读偏斜更糟糕的东西。在转账结束、集群进入静止之后，两个账户的版本链
并没有相互匹配的提交时间戳：

```
alice=21 versions bob=20 versions; unpaired: alice-only=[2 44] bob-only=[4]
```

`2` 和 `4` 是两次最初的单组装载，它们从不触及另一个组。**`44` 是一次真实提交，它存在于一个组中，
而在另一个组中缺失。** 也就是说，一个事务在一个组中提交了，而在另一个组中从未提交 —— 这正是
整个设计存在所要防止的那种原子性违背。

### 2.2 机制

追踪该事务在状态机中的提交路径：

```
seal    txn=3298534883359 key="0alice" ts=44     <- primary sealed: committed
publish key="0alice" ts=44 value="96"
commit-nolock txn=3298534883359 key="1bob" present=false
```

`1bob` 从未在 ts=44 被封印，它的版本也从未被发布。协调器要求组 1 提交 `1bob`，发现**没有锁**，
于是什么也没有发布。在一次运行中出现了 96 次这样的 `commit-nolock` 事件。

因此，那把次键锁在协调器的预写与提交之间被**丢弃**了。谁会丢弃锁？一个读者若发现一把*已过期*
的锁、而它的主键仍未封印，就会断定持有该锁的事务已死，并把它回滚：

```
lease lapses  ->  reader sees expired lock
              ->  primary still unsealed, so "owner is dead"
              ->  reader rolls the secondary lock back
coordinator   ->  seals the primary (too late)
              ->  commits a transaction whose other write is gone
```

当协调器为等另一个事务的锁而一直等到超时（最多 `resolveTimeout`，此处为 2 s），而租约只有 1 s
时，从预写到封印的窗口就会很长。

### 2.3 修复：恢复是一个决定，而不是一次猜测

根本缺陷在于，恢复过程从租约过期**推断**出死亡。有三处这样做：

```
ensurePrimaryResolved:  primary still prepared, lease expired -> StatePrepared
ResolveLock:            anything that is not StateCommitted    -> "provably dead", roll back
probePrimary:           primary group has no record            -> "aborted"
```

这三处都把「没有证据」当成了「死亡的证据」。租约只是一项承诺：持有者会续租这把锁；它完全没有
说明持有者是否仍能封印提交点，而封印才是真正使事务提交的动作。因此，读者可能丢弃一次写入，而
它的持有者本来正要提交它。

现在恢复是一次**通过 Raft 记录的比较并中止（compare-and-abort）**，它把「我可以丢弃这把锁吗？」
从一个推断变成了一个决定：

* 租约仍然限定恢复**在何时**可以被尝试 —— 当锁仍然有效时，持有者有权完成，读者则等待；
* 但中止本身是一条携带 `RecordDecision` 的 `CmdRollback`，它在**主组**上被应用，并且该组会先
  重新检查事务的状态。

如果事务已经提交，该组返回 `StatusAlreadyCommitted`，读者转而**发布**那次次键写入，而不是销毁
它。如果它尚未提交，该组就持久地记录 `StateAborted`。由于封印与这个决定由同一组上同一个 Raft
应用循环来应用，两者之中恰好只有一个能胜出 —— 这正是租约无法提供的互斥。

两项配套改动使这一点严密无隙：

* `Store.seal` 拒绝封印一个携带持久中止决定的事务（`StatusAlreadyAborted`）。没有它，协调器的
  封印可能在中止之后落地，从而复活一个另一半已经被丢弃的提交。
* `Txn.abortLockedGroups` **先中止主组**，并在这一步失败时提前返回，因此该决定总是先于任何次键
  回滚。只有到这时才可以丢弃锁，因为这个决定才是使丢弃它变得安全的东西。

`Txn.verifyLocksHeld` 仍然保留，作为一项廉价的提交前检查：它拒绝封印一把已经消失的锁，并报告
`LockRolledBackError`（可重试）。现在它只是通向一次干净失败的快速路径，而不是安全机制本身。

### 2.4 为什么这个修复是完备的

不存在任何一种交错，使得事务的一次写入被发布、而另一次被丢弃，因为发布需要提交决定，丢弃需要
中止决定，而两者都是在主组上按同一顺序应用的单条日志条目：

| 事件顺序 | 结果 |
| --- | --- |
| 协调器先封印 | 读者的比较并中止看到 `Committed`，于是发布次键写入。两次写入都落地。 |
| 读者先中止 | 主组记录 `StateAborted`；协调器的封印被拒绝，因此**两次**写入都不落地，事务被重试。 |
| 封印因路由原因而失败 | 协调器报告 `CommitUnknownError`，`Finish` 重新驱动各次键，而任何撞上遗留锁的读者都会查询主组并发布。 |

### 2.5 验证

暴露该缺陷的那项检查被保留为 `TestCommitTimestampsPairUpAcrossGroups`。每次转账都在两个组中各写
一个键，并且共享同一个提交时间戳，因此在静止之后，两条版本链必须包含相同的提交时间戳集合。它不
需要在值与事务之间建立对应关系，不需要假设哪个节点是权威的，也不需要任何时间窗口 —— 它把两个组
的持久状态相互比较。在修复之前，它在几次尝试之内就会失败；修复之后，24 次尝试全部通过。

两个确定性单元测试直接锁定这两种顺序，它们使用测试框架的时钟，因此不涉及任何墙钟等待：

* `TestSealedSecondaryIsNotLostWhenALeaseLapses` —— 让租约过期，先让一个读者行动，然后再提交；
  断言两个组对这次写入是否存在给出相同的答案。
* `TestLapsedLeaseAloneCannotAbortACommittedTransaction` —— 先封印，然后让租约过期并读取；断言
  读者是发布，而不是丢弃。

### 2.6 这次修复*没有*解决什么

§1.5 中的跨键快照缺口仍然存在：每组屏障无法覆盖一个已被决定、但其写入尚未被提议给某个组的事务。
`TestConcurrentTransfersPreserveInvariant` 审计单个快照，因此仍可能出于这个原因观察到总额不平衡。
这是一个*读*一致性问题，而不是持久性问题：如 §2.5 所确立，所有写入都在，但一次快照读并不保证
读到一个系统曾经处于过的状态。要弥合它，需要 §1.6 中授时服务侧的完成登记表。

## Part 3 — 关于不要怎样测试这个问题的一点说明

这里花掉的大部分时间都用在了错误的自检上。把它们记录下来，以免重蹈覆辙：

* **「提交成功了，所以把值读回来，与写入的值比较。」** 不可靠。并发事务会写入相同的值，因此一个
  值无法与某个事务对应起来。
* **在提交之后立即采样某个跟随者。** 这会把普通的复制滞后报告成写入丢失。
* **只采样一次「领导者」。** 领导权可能会移动；一个新上任的领导者可能还没有追上。
* **把跨组的水位最小值与某一个组的最新版本相比较。** 水位是组内的；这种比较没有意义。
* **在失败*之后*才转储版本链。** 后续提交会污染版本链，因此它不再显示审计时间戳处的状态。

真正有效的做法是：在静止之后比较**跨组的提交时间戳集合**（§2.1）。正是它暴露了真正的缺陷，因为
它不需要假设哪个节点是权威的，也不需要假设某个值在何时变得可见。
